# 要件定義書 – プロジェクト名：「（仮）LedgerMuse」  
※プロジェクト名は今後確定します。

## 1. プロジェクト概要  
**目的**  
個人利用から始めて将来的に商用運用も視野に、クラウド基盤（Google Cloud）上で「家計簿機能＋レシート画像OCR＋ナレッジ（メモ・検索）機能」を備えた Web アプリを構築し、認証・ファイルアップロード・DB接続など実務で使う API／インフラ設計を学習する。  
**範囲**  
- フロント：Next.js を用いた UI  
- バックエンド：Echo (Go フレームワーク) による API  
- クラウド基盤：Google Cloud フル活用（認証、DB、ストレージ、OCR 等）  
- 学習目的かつ低コスト運用を前提。将来、可用性・運用性・拡張性を強化可能な設計とする。  
- **インフラ構成管理（IaC）として Terraform を用い、コード化して管理・実践する。**  
- **利用する技術およびパッケージは、2025年11月時点で“安定しており、実務採用実績があり、将来性が見える”ものを選定する。**

## 2. ステークホルダー  
- 利用者（個人ユーザー）  
- 開発者／運用者（マスター）  
- 将来的な運用担当者／保守者  
- （将来）有料ユーザー／顧客  
- インフラ責任者（同上）

## 3. ビジネス要件  
- ユーザーがレシート画像をアップロードでき、OCR によって明細化される。  
- 支出データを記録・分類し、メモ・タグ付け・検索が可能。  
- 画像・添付ファイルの保存・取得が可能。  
- ユーザー単位にデータ隔離し、認証後のみアクセス可能。  
- 認証には安全な手法（最低でもユーザー／パスワード＋将来 MFA）を採用。  
- 学習用途ながらも「将来的に商用化する前提」で設計。  
- 固定費を最小限に抑え、運用コストを低く維持。  

## 4. 機能要件（高レベル）  
### フロントエンド  
- ログイン／サインアップ画面  
- レシート画像アップロード画面  
- 支出明細一覧、検索・フィルタ機能  
- ナレッジ（メモ・タグ）作成・編集・一覧表示  
- ダッシュボード（支出分析・タグ別集計）  

### バックエンド  
- API：認証、ユーザー管理、アップロード、OCRトリガー、明細取得、メモ管理  
- OCR連携：Google Cloud Vision 等を利用  
- ストレージ管理：画像や添付ファイルの保存・取得  
- データベース：ユーザー・支出・明細・メモ・タグのテーブル構造  
- 非同期処理：画像アップロード後に OCR をバックグラウンド実行  

### 非機能要件  
- セキュリティ：TLS／暗号化（転送中・保存中）／アクセス制御  
- スケーラビリティ：少ないアクセスから将来多アクセスを想定  
- 運用性：ログ・監視・CI/CDパイプラインあり  
- コスト：最小限のランニングコストで運用可能  
- 可用性：学習段階では１リージョン・低冗長でも可。将来拡張可能。  
- **技術・ライブラリ選定：2025年11月時点で安定実績のあるものを採用。**  
- **インフラ構成管理として Terraform を用い、環境（dev／staging／prod）の分離・リモート状態管理・モジュール化を実践。**

## 5. 技術スタック  
- フロント：Next.js (TypeScript)  
- バックエンド：Go + Echo フレームワーク  
- 認証／ユーザー管理：Google Cloud Identity Platform  
- データベース：Firestore（学習期）→将来的に Cloud SQL (PostgreSQL) 等へ移行検討  
- ストレージ：Cloud Storage  
- OCR：Cloud Vision API  
- 非同期処理／キュー：Pub/Sub + Cloud Tasks  
- インフラ：Terraform によるコード化  
- CI/CD：Cloud Build + Artifact Registry  
- 監視・ログ・アラート：Cloud Monitoring + Cloud Logging + Cloud Trace  
- セキュリティ強化：Cloud Armor + IAM 最小権限設計  

## 6. アーキテクチャ概要  
- フロント（Next.js）から API を呼び出す（HTTPS）。  
- API（Go/Echo）はユーザーネームスペースでルーティング、認証チェック、DBアクセス。  
- 画像アップロード時、Cloud Storage に保存 → Pub/Sub へメッセージ → ワーカーが OCR 処理 → 明細 DB に保存。  
- ダッシュボード・検索機能は DB／将来 BigQuery を参照。  
- 監視／ログ採集／アラート設置済。  
- インフラ定義・バージョン管理・デプロイ環境（dev/staging/prod）をTerraformで実現。

## 7. 運用・商用化に向けた拡張要件  
- CI/CD自動デプロイ、ユニットテスト・E2Eテスト。  
- モニタリング（メトリクス・トレース）、SLO／アラート設定。  
- 独自ドメイン＋HTTPS＋CDN＋WAF（Cloud Armor）。  
- DB冗長／マルチリージョン構成。  
- キャッシュ層（Memorystore／Redis）、CDNキャッシュ。  
- コスト監視・アラート（Billing Export → BigQuery 等）。  
- APIバージョニング、マイクロサービス分割。  

## 8. 制約・前提条件  
- 初期段階ではアクセス数が少ない想定。コスト最小化を最優先。  
- 学習目的ゆえに、完璧な商用構成ではなく「将来商用化できる土台」を整える。  
- 開発リソースは「マスター単独」で進行。  
- GCPを前提とし、他クラウド依存は避ける。  
- 技術選定において、2025年11月時点で安定実績のないベータ版・極端に採用例の少ないライブラリは原則避ける。  
- Terraformによる IaC を学習目的として最初から設計に盛り込む。

## 9. 成功基準／KPI  
- ユーザーがログイン～レシートアップロード～明細確認まで正常に完了できる。  
- アップロードから明細化（OCR含む）までの遅延が許容範囲（例：30秒以内）に収まる。  
- 運用コストが月額低額（例：数ドル〜数十ドル）に抑えられている。  
- ログ／監視／アラートが実装されており、障害発生時に通知される。  
- 次の拡張フェーズ（キャッシュ導入・マルチリージョン等）へ進める基盤が整っている。

## 10. リスクと対応策  
- **リスク**：学習用構成が本番トラフィック対応できない → **対応策**：将来拡張用の設計を初めから取り入れる。  
- **リスク**：コストが思ったより上がる → **対応策**：GCPの無料枠・低料金サービスを活用、コストアラート設定。  
- **リスク**：認証・セキュリティ設計が甘い → **対応策**：IAM最小権限設計・MFA将来実装。  
- **リスク**：運用監視体制が整っていない → **対応策**：ログ・メトリクス・アラートを早期に導入。  
- **リスク**：技術選定ミス（ベータ版採用など）により保守困難になる → **対応策**：採用技術を“2025年11月時点で安定”なものに限定・調査を行う。
